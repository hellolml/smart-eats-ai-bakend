# 候选地点筛选

接收原始提取的地点列表，进行去重、分类、多维度打分，输出带推荐详情的精选候选列表。

## 输入

1. **places** — 来自 `extract-places-from-travel-urls` 输出的结构化地点列表
2. **trip_meta** — 出行元数据，包括目的地、日期、人数、偏好、预算
3. **excluded_places** — 可选。用户明确要排除的地点
4. **user_added_places** — 可选。用户在候选列表输出后手动补充的地点，格式为自然语言列表或结构化输入。这些地点享有**最高优先级**，必须全部纳入最终候选列表

## 流程

### 1. 去重

- 合并名称相同或相似的地点（对名称和别名进行模糊匹配，如包含关系"西湖"⊂"杭州西湖"）。
- **地理位置校验**：名称相似但坐标距离 > 5km 的地点视为不同地点，不合并（避免"北京大学"和"清华大学"被误合并）。
- 合并条目中的 `mention_count`、`source_urls` 和 `context_snippets` 。
- 保留所有来源中最丰富的元数据（`associated_food`、`tags` 等字段取并集）。

### 1.5 避雷处理（在评分之前执行）

对每个候选地点检查是否存在"避雷"信息：

- **识别规则**：检查 `context_snippets` 中是否包含负面关键词（"避雷"、"踩雷"、"坑"、"别去"、"不值得"、"差评"、"难吃"等），以及 `author_rating` 是否为 `warned_against`。
- **处理策略**：
  - 若 ≥ 2 个来源明确避雷 → 将该地点移入"已排除"列表，`score` 强制设为 0，在最终展示时归入"⛔ 已排除的地点"区域，注明排除原因。
  - 若仅 1 个来源避雷但其他来源推荐 → 保留原评分，但在 `not_recommended_reason` 中注明"有来源提醒：{具体避雷原因}"，供用户参考。
- **展示**：被排除的避雷地点单独展示在候选列表末尾（见步骤 8.1），用户可选择恢复。

### 2. 分类

- 根据地点类型和上下文分配主类别。
- 使用标准类别：attraction、restaurant、cafe、hotel、shopping、nature、temple、museum、park、nightlife、transport_hub。
- 一个地点可能有次要类别标签（如景区内的餐厅）。

### 3. 多维度评分（0~10 分制）

对每个候选地点从四个维度评分：

- **热度（0~3）：** 基于 `mention_count` 和 `author_rating`
  - 被 3+ 来源强烈推荐 → 3
  - 被 2+ 来源推荐 → 2
  - 仅被提及一次 → 1
  - 被明确标记为"避雷"/"不推荐"，或 `context_snippets` 中出现负面关键词（如"踩雷"、"坑"、"别去"、"难吃"、"不值得"等）→ 0

- **偏好匹配（0~3）：** 地点与用户偏好的匹配程度
  - 直接匹配（用户喜欢自然，地点是自然类）→ 3
  - 相关匹配（用户喜欢文化，地点是博物馆）→ 2
  - 中性 → 1
  - 冲突（用户不喜欢拥挤，地点总是很挤）→ 0
  - **交叉加分**：当地点同时满足用户的多个偏好时，额外 +0.5（上限仍为 3）。例如：用户偏好"美食+自然风光"，某自然景点的 `associated_food` 中有攻略推荐的美食信息 → 基础分 3（自然匹配）+ 0.5（关联美食命中美食偏好）= 3（封顶）。这使得"自然景点+关联美食"的组合在排序中更靠前。

- **时间适配（0~2）：** 地点是否适合行程时长和季节
  - 最佳季节 + 时间充裕 → 2
  - 可接受 → 1
  - 季节不符或时间不足 → 0

- **预算适配（0~2）：** 费用是否符合用户预算级别
  - 在预算内 → 2
  - 略超预算 → 1
  - 明显超预算 → 0

### 4. POI 验证与补充（调用高德 后端高德工具封装）

> **会话级 POI 缓存（两级 key 设计）：**
> - **缓存范围**：仅限当前会话，会话结束即丢弃。不持久化到文件，因为 POI 信息会变更（店铺关门、营业时间调整等），长期缓存容易过期。
> - **实现方式**：LLM 上文记忆。同一会话中查过的 POI 结果已在文中，直接复用即可。
> - **第一级（查询 key）**： 用 `amap_poi_keyword`（攻略原文关键词）匹配。若同一关键词在文中已有查询结果，直接复用。
> - **第二级（结果去重 key）**： 用 `amap_poi_id`（高德 POI ID）做去重。不同关键词（如「老妈蹄花」和「欢太爱蹄花」）若查到相同的 `amap_poi_id`，识别为同一地点，合并而非重复。
> - **别名处理**：高德搜索返回的 `name` 可能与攻略原文不同（如「宽窄巷子」→「宽窄巷子景区」）。以高德返回的 `name` 为准，但保留攻略原文作为 `amap_poi_keyword` 以便溯源。

对每个去重后的候选地点，**先查询 POI 缓存**：
- **查询 key 命中中**：上文已有该 `amap_poi_keyword` 的查询结果，直接复用 POI 信息，跳过高德 API 调用。
- **查询 key 未命中中但高德 key 命中中**：上文中虽无该关键词，但存在另一个关键词查到了相同 `amap_poi_id` 的结果（别名情况），直接复用。
- **均未命中**：调用 `travel_search_poi` 验证，查询成功后结果自然存入上下文，供后续复用。

执行 `travel_search_poi` 验证并补充全 POI 信息（禁止绕过后端工具直接调用高德 REST API）。
- 如搜索命中：
  - 设置 `poi_verified: true`。
  - 填充 `amap_poi_id`（高德 POI ID）。
  - 填充 `longitude` 和 `latitude`（精确坐标）。
  - 用搜索结果中的地址更新候选地点的 `address` 字段。
  - 填充 `business_hours`（营业时间），来自高德返回的 `business_hours` 字段。若该字段为空，则设为 `null`，表示未获取到营业时间（视为全天可访问）。
- 如搜索未命中：
  - 设置 `poi_verified: false`。
  - 尝试缩短关键词重新搜索（如 "杭州知味观湖滨店" → "知味观"）。
  - 若仍未命中，保留候选但在 `warnings` 中标注"未在高德找到对应 POI"。
- 对于已验证 POI 的候选，可执行 `travel_search_nearby_poi` 识别附近其他候选，填充 `nearby_candidates`。

### 5. 生成推荐信息

对每个候选地点：
- 撰写简洁的 `recommended_reason`（为什么值得去，1~2 句话）。
- 撰写 `not_recommended_reason`（如有：人多、天气、费用等顾虑）。
- 确定 `recommended_time_slots` 和 `best_visit_time`。
- 根据来源上下文和常识估计 `crowd_level`。
- 识别 `nearby_candidates` 用于行程聚类。

### 6. 区域校验

对所有候选地点（包括攻略提取的和后续用户补充的）进行目的区域校验：

- 利用 POI 验证返回的坐标和地址，检查地点是否在 `trip_meta.destination` 所指定的区域范围内。
- **不在目的区域内的地点**：不自动删除，但在候选列表中附带温馨提示：
  ```
  ⚠️ 温馨提示："{地点名}" 不在 {destination} 区域内（实际位于 {actual_region}），纳入行程可能增加较多交通时间，请确认是否保留。
  ```
- 用户确认保留后正常纳入行程。

### 7. 排序和过滤

- 按总分降序排列。
- 过滤掉分数低于 3.0 的候选（除非候选池太小）。
- 确保类别多样性（每天行程至少 1-2 个餐厅）。
- 为 "必去" 地点（分数 >= 8）添加标签。

### 8. 分类展示与用户确认（必须步骤）

> **所有候选地点必须经过用户确认后，才能进入行程规划。此步骤不可跳过。**

#### 8.1 分类展示

将候选地点按以下三大类分组展示给用户。**每个分类内部按评分降序排列**，评分相同时依次按下规则打破平局：

1. `source: "user_added"` 优先于 `source: "extracted"`
2. `mention_count` 降序（被更多攻略提及的优先）
3. `score_breakdown.preference_match` 降序（偏好匹配度高的优先）

**🏞 景点类**（含 nature、attraction、temple、museum、park）：

- 每类末尾显示小计数量。

#### 8.2 用户操作

展示完毕后，引导用户进行以下操作：

1. **删除**：用户可指定不想要的地点（如"去掉第 3 个景点"或"不要 XX"），从候选列表中移除。
2. **补充**：用户可补充想去的景点、住宿、美食，格式为自然语言。
3. **确认**：用户表示"没问题"、"可以了"、"确认"等，进入行程规划。

#### 8.3 用户补充地点处理

当用户补充地点时，对每个补充地点执行以下操作：

- **解析用户输入**：用户可能以自然语言（如"我还想去奈良公园和一兰拉面"）或列表形式提供，需提取地点名称和可能的类别信息。
- **标记来源**：设置 `source: "user_added"`，与攻略提取的 `source: "extracted"` 区分。
- **强制最高评分**：用户补充的地点自动获得满分 **10 分**，`score_breakdown` 各维度满分。
- **添加 must-visit 标签**：自动添加 `tags: ["must-visit", "user-specified"]`。
- **POI 验证**：同样执行步骤 4 的 POI 验证与补全流程（执行 `travel_search_poi`）。
- **分类**：根据地点名称和上下文推断类别。
- **去重检查**：若用户补充的地点与已有候选重复，将已有候选的 `source` 更新为 `"user_added"`，提升至最高优先级。
- **区域校验**：同样执行步骤 6 的区域校验，不在目的区域的附带温馨提示。

**用户补充地点绝不会被过滤掉**，即使 POI 验证失败或信息不完整，也必须保留在候选列表中。

##### 美食类补充的特殊约束

用户补充的美食类地点（restaurant、cafe、nightlife）必须是**具体的店名**，且能在高德地图中查到对应 POI：

- **合法示例**：`顶顶牛干锅牦牛肉` 、 `沙洲夜市` 、 `知味观湖滨店` → 执行 `travel_search_poi` 能查到 POI ✅
- **不合法示例**：`当地特色小吃` 、 `手抓羊肉` 、 `好吃的面馆` → 泛化描述，非具体店名 ❌

当用户补充的美食不符合要求时，返回提示：
```
💡 美食补充需要提供具体的店名（如"顶顶牛干锅牦牛肉"），方便我在高德地图上精确标注。"{"用户输入"}" 看起来不是一个具体的店名，请补充完整的店铺名称。
```
#### 8.4 补充后重新展示

用户每次补充或删除操作后，重新按分类展示更新后的候选列表，直到用户明确确认。

#### 8.5 确认完成

用户确认后，将最终候选列表标记为 `candidates_confirmed`，传递给下游 `generate-itinerary-from-candidates` 进行行程规划。

## 示例

**输入：** 从 3 个 URL 提取出 12 个地点，trip_meta: {destination: "杭州", preferences: ["美食", "自然"], travelers: 2, budget: "moderate"}

**执行步骤：**
1. 合并"灵隐寺"和"灵隐飞来峰" → 单条记录，`mention_count` 累加
2. 西湖评分：热度 3 + 偏好 3（自然）+ 时间 2 + 预算 2 = 10 → 必去
3. 知味观评分：热度 2 + 偏好 3（美食）+ 时间 2 + 预算 2 = 9
4. 某高端日料评分：热度 1 + 偏好 2 + 时间 2 + 预算 0 = 5

**结果：** 10 个候选按分数排序，西湖和知味观标记为必去。

## 故障排查

**筛选后候选太少。**
原因：评分标准严格且来源数据有限。
解决方案：降低阈值，或将 "仅被提及" 的地点也纳入，并标注验证度较低。

**所有候选都是同一类别。**
原因：来源文章全是美食博客或是景点攻略。
解决方案：向协调 skill 报告失衡。建议用户提供更多样化的 URL 或手动补充其他类型地点。

**分数相同。**
原因：多个地点的得分完全一样。
解决方案：依次按 mention_count、preference_match、字母顺序排序打破平局。

**POI 验证失败率过高。**
原因：攻略中的地点名称不规范，或为非正式简称。
解决方案：尝试多种关键词变体搜索。对于完全无法验证的地点，保留但降低评分权重。
